## 导入方式

这些文件是仓库中的源资料，不会因为放入本目录就自动写入知识库。启动应用后：

1. 进入“资料管理”。
2. 点击“导入系统资料”。
3. 等待资料状态变为“成功”，检查分块数量和处理说明。
4. 在问答、评测和检索实验中验证引用和回答行为。

手动选择 `documents/` 下的文件上传仅用于开发和调试，不替代系统资料导入流程。

## source_key、SHA-256 与状态

后端扫描 `documents/` 时，为每个文件生成：

- `source_key`：稳定的系统资料身份，格式为 `builtin:<相对路径>`。
- `source_hash`：源文件内容的 SHA-256，用于识别内容版本。
- `source_type=BUILTIN`：表示资料来自本目录；用户自行上传的资料为 `source_type=UPLOAD`。

系统资料状态由源清单和 SQLite 中的资料记录比较得到：

| 状态 | 含义 |
| --- | --- |
| `MISSING` | 源资料存在，但尚未建立对应导入记录 |
| `PROCESSING` | 正在解析、分块、向量化或建立索引 |
| `SUCCESS` | 已导入且记录的 hash 与当前源文件一致 |
| `FAILED` | 最近一次导入失败，可以重试 |
| `OUTDATED` | 记录存在但 hash 已变化，需要重新导入 |

内容变化的完整链路是：

```text
修改 documents/ 文件
→ SHA-256 变化
→ 状态变为 OUTDATED
→ 再次点击“导入系统资料”
→ 复制新的工作副本
→ 重建对应 Chunk 与 production FAISS 向量
```

导入时系统资料会复制到 `uploads/` 作为运行时工作副本，再按普通资料的 Loader、Splitter、Embedding、SQLite 和 FAISS 链路顺序处理。`reference-data/` 是只读源，`uploads/` 不是源资料的替代品。

同名但 hash 不同的用户上传资料可以与系统资料共存；如果历史上传文件与系统源文件 hash 完全一致，系统可以认领该工作副本为对应的 `BUILTIN` 资料。

## 资料变更质量门禁

修改本目录中的任何资料后，提交前必须：

1. 在应用中再次执行“导入系统资料”。
2. 通过 `GET /api/documents/builtin/status` 确认全部系统资料为 `SUCCESS`，没有 `MISSING`、`FAILED` 或 `OUTDATED`。
3. 运行官方 baseline 评测，记录回答、拒答率和引用命中变化。
4. 检查关键问题是否命中预期文件和 Chunk。
5. 对修改涉及的主题执行关键回归，确认没有引入明显错误或过期表述。

示例检查入口：

#### Windows PowerShell

```powershell
curl.exe -fsS http://127.0.0.1:8000/api/documents/builtin/status
cd backend
.\.venv\Scripts\python.exe -m app.scripts.audit_evaluation_baseline
```

#### macOS / Linux

```bash
curl -fsS http://127.0.0.1:8000/api/documents/builtin/status
cd backend
.venv/bin/python -m app.scripts.audit_evaluation_baseline
```

## 维护约定

- 只提交已获授权或可公开使用的资料，不要放入密钥、个人隐私、真实咨询记录或运行时数据库文件。
- 修改资料时保留清晰的文件名，并在提交说明中记录来源、发布日期、生效日期或版本变化；无法确认的元数据应明确标记待补充。
- 不要手工修改 `data/`、`uploads/` 或 FAISS 索引来“修复”系统资料状态；通过源文件和一键导入流程更新。
- `data/`、`uploads/` 和 FAISS 索引属于运行时数据，不放在本目录中。
